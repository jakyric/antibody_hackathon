# S1a: RFD4-Proteina VHH design on JapanFold

De novo-track VHHs against HER2 domain IV, generated by the hosted JapanFold `rfd4` (RFD4-Proteina, protocol `rfd4-binder`)
on a fixed, structurally validated VHH framework, aimed at the trastuzumab epitope. Output feeds S2 (rules, framework
diversification), S3 (OpenFold3 + orthogonal scoring) and S4 (properties). Reasoning and evidence: [decisions.md](decisions.md).

## What it does

```
RCSB 3EAK / VM caplacizumab example ──► prep_inputs.py ──► frameworks/*.json + inputs/*_on_her2*.cif
(framework + CDR map, framework placed where                    (HER2 chains A,C + framework chain B, in the 1N8Z frame)
 trastuzumab's VH sits in 1N8Z)
                                              │
                         run_design.py (threads, resumable) ──► POST /v1/designs  protocol=rfd4-binder
                                              │                   contig  A489-580,/0,C591-607,/0,B1-22,<CDR1>,B39-53,<CDR2>,B62-99,<CDR3>,B118-127
                                              │                   hotspots  residue level from targets/epitope.json
                                              ▼
              results/denovo/designs_rfd4jf.csv  (flushed after EVERY finished job)   + designs/<id>.cif (VHH + HER2, 3 chains)
              results/denovo/geom_rfd4jf.csv     (contacts, clashes, hotspot/epitope contacts: a cheap pre-filter, NOT binding evidence)
                                              ▲
                  feedback.py ◄── results/denovo/score_orth.csv / score_of3.csv (S3): shifts jobs toward the cells that score well
```

Facts that shape everything (details and evidence in decisions.md): the hosted wrapper fixes the kept residues' sequence AND puts
all kept backbone (HER2 + framework) in one rigid coordinate group, so the framework pose is what we submit (superposed on
trastuzumab's VH); CDR lengths are drawn from the requested ranges; every design keeps the framework 100% identical to its parent
(S2 must diversify it for the <70% identity rule).

## Run

```bash
PY=denovo/.venv/bin/python
export JAPANFOLD_API_KEY=...                                       # never printed or logged
$PY denovo/s1_design/prep_inputs.py                                # once: frameworks/*.json, inputs/*.cif (needs denovo/targets/READY)
$PY denovo/s1_design/prep_caa.py                                   # once: wave-2 inputs with C104-A105-A106 kept fixed (grafts A105/A106 onto capla)
$PY denovo/s1_design/run_design.py --auto --dry-run                # show the next plan and contigs, costs nothing

# WAVE 1 (historical, uniform grid, stopped): 24 cells x r0-r2, CDR3 block 12-16 / 16-21 starting at IMGT 105 (command was --reps 3 --workers 12)

# WAVE 2 = the campaign: adaptive waves, CAA fixed, CDR3 ranges per framework (final: c3m2 = capla 10-16, bcii10 13-16 designed, IMGT block 12-18),
# re-planned each wave by feedback.py. RESUME / EXTEND = re-run this (it first collects any finished jobs, then plans new ones with fresh seeds):
$PY denovo/s1_design/run_design.py --auto --until HH:MM --jobs-per-wave 24 --workers 40 --max-inflight 12 --budget 28

# loop-aware batch (modelled HER2 incl. the 581-590 loop, generator rfd4jf-loop, CIFs in results/denovo/designs_loop/, design_cif empty)
$PY denovo/s1_design/run_design.py --loop-smoke                    # one job, prints diagnostics, touches no CSV
$PY denovo/s1_design/run_design.py --loop-batch 9 --loop-rep 0 --until HH:MM   # 9 jobs x 8 designs; use --loop-rep 1 for NEW seeds
# only ONE process may write designs_rfd4jf.csv at a time (each keeps its rows in memory): stop the other loop before starting this one.

$PY denovo/s1_design/feedback.py                                   # per-cell table: geometry + OF3/consensus, writes feedback.csv
$PY denovo/s1_design/summary.py                                    # campaign summary
```

Resume = re-run the same command. Every job has a stable name (`s1a-<fw>-<hotspots>-<cdr3 range>-<pose>-r<rep>`, seed fixed by
cell and repeat), its JapanFold id is cached in `results/denovo/jobs/`, and finished jobs are skipped, so nothing is paid twice.
To extend a uniform run raise `--reps`; the auto mode continues each cell at its next unused repeat. Spend is accumulated in
`spend_ledger.jsonl` and `--budget` (default $14 of the $15 cap) is checked across runs.

## End state (15:25)

`results/denovo/designs_rfd4jf.csv`: 1480 rows, all with a unique `vhh_seq` (capla 782, bcii10 698; 72 of them `rfd4jf-loop`); 1092 have an IMGT-block CDR3 of 12-18 aa. 94-149 designs in each framework x hotspot x pose cell.
Spend 3.7 USD. The CSV is only ever written with unique sequences (asserted on every write; `load_rows()` dedupes at start-up).
Side files: `duplicates_removed.csv` (986 rows from the seed-overlap bug, see decisions D7), `out_of_range_cdr3.csv` (147 designs collected after the length cap changed), `failed_jobs.jsonl`, `plan_log.jsonl` (14 plans), `cell_table.md`, `feedback.csv`.

## Grid

| axis | values | why |
|---|---|---|
| framework | `bcii10` (hNbBCII10-FGLA, PDB 3EAK), `capla` (caplacizumab VHH framework) | humanised and camelid-hallmark frameworks, both with structures |
| hotspot set | `hs1_core` (6 atoms, dominant patch 557-573), `hs2_broad` (12), `hs3_alt_patch` (6, 591-603 patch) | from the trastuzumab contacts in 1N8Z |
| CDR3 length block | wave 1: `c3a` 12-16, `c3b` 16-21 (block starts at IMGT 105, so the invariant A105/A106 were redesigned). **Wave 2: `c3n` = C104-A105-A106 fixed + 15-20 designed, i.e. 17-22 aa in the `cdr3` column** | S2 found the VM abguard de novo pass rate rises with total length (bcii10: 0% at 12-13, 21% at 14, 80-100% at 18-21); the monoyield paper says CDR3 packs on the invariant CAA |
| pose | `p0` trastuzumab-VH pose, `p1` rotated 10-14 degrees and 1.5 A away | one rigid pose is the model's main constraint |
| wave 2 only | `caa_fixed=1` in `params_json`; for `capla` the A105/A106 backbone is grafted from bcii10 (superposition RMSD 0.09 A, C104-N bond 1.31 A) because the example structure has no CDR3 residues | keeps the CDR3 anchor; `params_json` also has `cdr3_designed_len`, `cdr3_total_len` |
| fixed | `recipe=high/front_loaded`, `nsteps=60`, 8 designs per job | upstream antibody setting; fewer steps is a different, worse model |

CDR1 and CDR2 length ranges: 13-17 / 8-10 (`bcii10`), 12-15 / 9-11 (`capla`). CDR definition: IMGT 24-40, 56-65, 105-117 (as in
the RFD4 antibody examples).

## Known failure modes

* HER2 residues 581-590 are missing in 1N8Z: HER2 must be submitted as two chains (A, C) and the contig must separate them with `/0`.
* Two kept stretches of the same chain with nothing between them are refused by the API; design a segment or break the chain.
* The queue, not the cost, is the bottleneck: the fleet was saturated (about 260/260 chips) and the account runs about 8 jobs at once across the
  team's stages, so a design job can wait many minutes behind scoring batches. Cost is about $0.0017 per design.
* `HTTP 402 ... runs still in progress can cost up to $X` is NOT an empty wallet: in-flight runs (S3's big batches) reserve their maximum cost, so a new run
  waits. The runner backs off and retries (up to 40 times); a real out-of-credit 402 has different text and fails the job.
* Re-starting `run_design.py` mid-campaign is safe: every submitted job id is cached and `recover_jobs()` collects finished jobs that were never written.
  (Learned the hard way: a pool with as many threads as in-flight slots blocks on queued jobs while finished ones wait; hence 40 threads, `--max-inflight 12`.)
* `p1` poses are a gamble: geometry columns show whether they pay off (see decisions.md D6).
* A job with seed S makes designs with seeds S..S+7: space job seeds by >= 8 (`new_seed()`), otherwise repeats re-make the same designs (decisions D7).
* Only one process at a time may write the designs CSV; the runner asserts uniqueness on every write but cannot see another process's rows.
